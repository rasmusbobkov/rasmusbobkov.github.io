# Spec Kit and EGM workflow

The [constitution](../../.specify/memory/constitution.md) defines the project workflow. Host authority, assigned scope and consent remain higher. Spec Kit 1.2.5 and the independently maintained EGM port 0.9.1 provide project-local skills; their presence does not authorize implementation, merge or deployment.

## Planning and implementation boundary

Planning and implementation are separate tracks. Spec Kit → applicable Lavish visual-intent feedback → Goldfish prepares and reviews specifications and feature/bug plans under the existing zero/five classification. An understood correction with current accepted intent still needs no new EGM planning phase. Implementation follows first mate → native no-mistakes validation → PR: execute the accepted story, independently review the committed change, run criterion-specific and project checks, confirm documentation currency and obtain separate proof judgment before publication. Ordinary scope-preserving implementation repairs do not restart the planning track; changed intent returns to the affected planning step within actual authority. This distinction changes no finite allowance, consent, merge or deployment boundary and adds no external runner.

## Artifacts and commands

Find the existing canonical issue and owner before work. Product planning and technical issues retain their established tracker roles; one outcome has one canonical issue, not a duplicate in both. Keep private tracker details out of shared files. Roadmaps and host tasks are derived views or assignments.

Those instructions remain present and can conflict with the constitution's canonical feature specification and plan. Keep the concepts brief as a working input and supply it explicitly when authorized; do not assume automatic ingestion. Establish or update the authorized feature `spec.md`, then refine the same feature `plan.md`. Do not follow the separate-design handoff as an accepted design master. A separately authorized noncanonical RFC remains subject to host consent. This disposition does not edit the upstream package or grant permission to publish.

The latter remains available only when separately authorized; its feature/task identity repair avoids collisions. When the assignment excludes writing that pointer, set `SPECIFY_FEATURE_NO_PERSIST=1` for feature-selection scripts; scripts calling the helper directly may instead use `--no-persist`. Explicit selection alone otherwise persists the pointer. Keep discussion summaries and review reports in the authorized task evidence or artifact directory, not in the canonical plan; refine existing plan sections without overwriting unrelated content.

## Review policy and limits

### Classify impact, not size

The first mate records the canonical issue, owner, current accepted intent/artifact revisions, classification and reason. A **small understood correction** means a bounded correction with a known cause, scope and expected result and no significant trigger. It takes zero EGM phases, no EGM-Lite substitute and no automatic new requirements checklist. Reuse applicable accepted artifacts; missing/stale inputs stop affected work for reconciliation.

New behavior, shared contracts, saved-data/security boundaries, workflow changes, unresolved architecture and ambiguity take all five EGM design phases. This exception removes the former single relevant phase for small corrections; it does not remove significant-change scrutiny. [Decision 0011](../decisions/0011-minimal-review-routing.md) narrowly supersedes that portion of decision 0010.

### Visual intent before the first review

For UI-changing intent, Codex generates local HTML from the current canonical specification and the product’s actual design system. Use the supported local Lavish route to render, annotate and submit feedback before the FIRST Goldfish review, including brainstorm’s early concept review. Non-review clarification may prepare the mock; an early review cannot bypass this gate. Revise canonical intent first, then its mock. The first mate verifies recorded human acceptance of the CURRENT version-linked spec/mock visual direction before dispatch. Rejection or material visual change returns to visual review. Annotations, feedback submission, silence, session end, agent edits and reply receipt are not acceptance. Visual acceptance grants neither implementation/resource permission nor behavior proof. Non-UI work records justified inapplicability; unavailable capability or permission stops the affected step.

The local route is Kun Chen’s installed lavish-axi 0.1.96: Codex generates; Lavish renders and returns submitted feedback, not another generative provider. Read its installed skill and current design/plan/input/reply guidance before authoring HTML. The feature’s [canonical operational procedure](../../specs/002-review-routing/plan.md#supported-local-lavish-operation-and-safety) owns exact operation. Keep telemetry off, explicit loopback host/link on every command, isolated task state, local/disposable assets/data and one port selected unused before launch and retained for the session. Never inspect or stop another session. No share/upload/publication, non-loopback exposure, installation/hooks/accounts, provider fallback or mock-collected host consent is authorized.

Maintain at most one concurrent owned tracked completion-notifying poll on the same canonical HTML path and isolated environment. Each poll delivers one submission and returns: consume it fully, revise spec then mock within authority, and rearm while visual review remains pending. Standalone reply does not rearm; absent/failed listening is not monitoring. Terminal human end does not auto-reopen. Register owned session/server/listener cleanup with launch and complete it before task closure. Establish actual rendering, two deliveries and agent resumptions with intervening revision/rearm, and cleanup before claiming operation. Documented availability or reply receipt alone proves none of these.

### Story criteria and proof

Before implementation, record each story’s criteria, actual verification method and derived task/check/evidence links. Execute checks that see those criteria, end-to-end where needed. Code, a generic suite pass, a suitable mock, labels or design approval cannot complete a story. Failure returns to authorized repair and affected retest/review; missing proof blocks completion. An explicitly approved exception stays an exception, never a pass. Independent evidence judgment is separate from author execution. A disposable workflow visual cannot prove product UI acceptance or the dependent real-route rollout.

### Significant-change design sequence

1. Initial zoom out: skeptical architect and inventive catalyst examine root problem, simplicity, reuse and alternatives; aggregate both actual reports.
2. Standalone comprehension: one fresh reader paraphrases the plan and existing system from the plan alone as design input. Exclude author conversation, explanatory sources, previous findings and automatic linked-file expansion; preserve the full paraphrase.
3. Design critique: design, structural and style personas examine high-level decisions and clarity under the installed feature-spec standard; retain its distinct report and dispositions.
4. Intermediate zoom out: skeptical architect reads the full current plan with actual earlier findings/dispositions and checks coherence after repairs.
5. Implementation readiness: readiness, codebase-details and style personas examine detailed executable steps under the installed readiness standard. Have current derived tasks ready first. Exactly one assigned readiness reviewer applies Spec Kit analyze to the same pinned spec/plan/tasks in that report, with separate consistency/coverage and EGM findings. Other personas do not duplicate that analysis.

Use explicit files under `.specify/extensions/egm/agents/`; names and filenames do not uniformly match. Launch only the next phase whose actual pinned inputs and prior clearance exist. Do not reserve later reviewers with empty assignments/sessions. Record actual inputs, hashes, reads, procedural/context boundaries, required reviewers, status, findings and dispositions. Report the observed prefix and unassigned/unfinished remainder; five actual assignment identities exist only once the last phase is genuinely input-ready and assigned, and five completed results require actual completion.

Custom requirements checklists address a concrete domain gap only, not another general reread or proof that code works. Spec Kit analyze/checklist are artifact/requirement assessments, not separate core code-review executables. The installed `specify` CLI supports setup and template discovery (for example, `specify preset resolve plan-template`); agents follow project-local procedures and the first mate coordinates native reviews. Do not invent `specify plan`/`specify review` commands or infer automatic delegation from template resolution.

### Findings, limits and continuation

A missing required reviewer or unresolved Blocker/Major stops the affected phase or delivery judgment. Nits alone do not block. The author proposes resolver dispositions; fixes require independent verification and do not retroactively make a failed round clean. A contest needs concrete counter-evidence within permitted reviewer inputs and independent agreement; a comprehension gap cannot be contested using unread explanations. Disagreement remains open for first-mate reconciliation. Accepted-risk labels cannot waive accepted requirements, required safety boundaries or higher authority. A captain-owned exception needs an actual explicit decision and reconciled artifacts; no such label fabricates a clean result.

#### One complete clean aggregate

For eligible new critique and implementation-readiness invocations, apply the [constitution's project override](../../.specify/memory/constitution.md#planning-convergence-override). It replaces only the two-consecutive-clean convergence threshold in §2.4 of the installed [review-loop skill](../../.agents/skills/speckit-egm-review-loop/SKILL.md#24-iteration-check--turn-boundary) and its [command mirror](../../.specify/extensions/egm/commands/speckit.egm.review-loop.md#24-iteration-check--turn-boundary). Leave those files unchanged. Apply the override only after separately authorized integration and verified alignment of the applicable standing direction. At invocation start, verify and record actual method and direction revisions and pin the effective rule. Stop affected work if the applicable instructions conflict or cannot be established. Underway invocations retain their starting rule and counters; this change's own planning used two consecutive clean rounds.

Critique assigns `design_critic.md`, `structural.md` and `style.md`; design and structural apply `feature-spec-standard.md`. Readiness assigns `implementation_readiness.md`, `codebase_details.md` and `style.md`; readiness and codebase apply `implementation-readiness-standard.md`. Style uses its persona rubric. Each required role independently records its scope, actual reads and findings on matching current inputs. Hashes identify inputs, not what was read. Exactly one assigned readiness reviewer analyzes the same pinned spec, plan and tasks and separates Spec Kit consistency and coverage findings from EGM findings. Link overlapping findings without counting one defect twice.

Determine cleanliness before repairs. A complete aggregate is clean when all three roles completed with matching current coverage and no unresolved Blocker or Major. Attribute and disposition Nits separately; they do not require confirmation. A missing, stale, unavailable or failed reviewer is not zero findings. Retry a failed reviewer once on the same immutable pin; after a second failure record the role as not run and stop affected clearance. Author self-review cannot fill a role. One clean aggregate meets the new threshold; converge without automatic confirmation only when no separate stop remains. Record a clean-but-held result as clean, with its hold intact.

#### Repairs and current coverage

Preserve the original failed verdict. After a repair, pin the revised inputs and delta. Within the applicable allowance, independently verify affected decisions, findings, scenarios and explanations. For every retained portion, its original independent reviewer must explicitly confirm applicability to the current bundle and delta, even if that reviewer also rechecks an affected portion. Combine only verified and explicitly reconfirmed coverage. A replacement must independently cover its full current role, including relevant unchanged parts; a delta-only read cannot inherit coverage. Record what each reviewer read, verified and confirmed. One role cannot fill another. If coverage or impact is uncertain, broaden review within authority or stop. A material change invalidates affected coverage and prior phase judgments. Reopen recurring fixed findings. A later complete clean aggregate can converge under the new rule only if no separate stop remains.

#### Extra review and finite accounting

Commission extra review only for a named high-consequence uncertainty or conflicting finding, not generic confidence. Record the evidence, deciding question, affected scope, pinned inputs, independent reviewer, expected signal, authorized round or finite exception, and stopping condition. An inconclusive answer leaves the stop in place. Available slots are not authority.

Critique and readiness retain at most five inner rounds per invocation. Record phase, invocation, input pin, inner round, outer use and remaining authority separately. A review or repair-verification batch spends its applicable slot at actual launch, once for the batch, not at reservation or per reviewer. All roles in a batch use one immutable pin. If inputs change before aggregation, retain its findings and record the batch as nonclean or interrupted; the spent slot is not returned and the new inputs are not cleared. A retry cannot cover a changed pin; any new batch needs actual launch authority and its own accounting.

Under the new rule, a complete clean fifth round can converge if no stop remains. If round 4 was clean but held by a named question and a same-pin verification batch is authorized in slot 5, round 5 needs its own complete current aggregate. The deciding reviewer covers only its assigned scope. Original independent reviewers must explicitly confirm the applicability of each retained portion to the same bundle and the answer's impact; they need not reread confirmed unaffected portions. A replacement covers its full current role. Aggregate all three roles before repairs. A positive answer alone does not release round 4. If coverage is missing, the answer is inconclusive, the round is nonclean or another stop remains, preserve the held verdict, record slot 5 as spent and stop at the cap. Do not launch a sixth ordinary round or use the outer re-audit to bypass the cap. A distinct finite captain decision is required to continue stopped work.

Preserve the installed outer wrapper's single stage re-audit after repair. It is for independent stage-level verification after the prior invocation returns; it starts a separate complete invocation only with input-ready work, actual authority and no unreconciled stop. It is not another round of the prior invocation or an escape from cap or churn. Direct comprehension has no inner antagonistic loop: initial plan-only assessment plus one ordinary re-audit, then stop for an explicit finite exception if required. Churn means a new finding at an applied fix's scope that reverting the fix would resolve. Drafting, renamed verification and new invocations do not reset existing accounts or transfer unused slots.

Churn, exhausted allowances or unresolved blockers stop for the host-governed decision. Keep actual invocation/round counts, original findings and justified dispositions. Within accepted scope and actual remaining authority, the first mate continues input-ready phases, ordinary failures and scope-preserving repairs without another routine human continuation question. Human product/scope decisions, unresolved intent, resource access/cost/sensitive effects, evidence exceptions and cap/churn extensions still stop for an actual decision; numerical budget is not launch authority. Any exception names the stopped stage, limit, pinned input and finite scope; extending one limit does not extend another. Host authority overrides generated automatic-advance, nested-spawn or chat-gate instructions. Automatic spawning/registration and a complete automated loop remain unproven; native coordinated review is not proof of them.

For later changes, record affected files, requirements, scenarios, prior findings and evidence, and proposed repeats; an independent reviewer verifies coverage, with disputes reconciled by the first mate. New design decisions reopen affected design scrutiny. Wording review uses its applicable allowance or specifically authorized continuation; it does not grant an exhausted comprehension retry. Retain unchanged evidence only with an explicit applicability explanation, and retain the final full gate/current hosted checks.

### One native delivery-review track

After authorized implementation is committed, the author supplies accepted intent, full diff, changed scope and success/adverse scenarios for the first mate to arrange independent native code/documentation/scenario review. Its judgment assesses accepted intent, preserved behavior and coverage at that version. Repair owned findings and obtain affected review; design approval cannot clear implementation defects.

The author runs actual checks and authorized observations, retaining exact commands, environment, version, results and artifacts. A separate independent proof judgment reads that evidence against required scenarios without rerunning the suite. One track contains these separate judgments, not one model call, and adds no external no-mistakes agent pipeline. Current care settings do not change automatically; attestation depends on actual accepted version-bound review/evidence records, never care labels alone.

BEFORE publishing a new or updated PR version, require current independent committed-change/scenario review, actual story/project checks, documentation currency and separate proof judgment. Hosted checks follow publication and must pass at that version. A later affected edit renews its review/check applicability. Pre-merge delivery requires independent change review without unresolved blocking findings, passing required local/hosted checks and accepted pre-merge proof. Missing required reviewer/proof remains a gap. Documentation-only work does not invent an application journey; state the absence of an executable changed surface. Record separately the first-mate-owned post-merge direction replacement and real fresh-session route observations; do not pretend these ran before merge. Merge and deployment remain separate authority.

### Publication gate before pushing an existing pull request

Pushing a branch already attached to a PR publishes a new version immediately; a later story or merge preflight cannot prevent that earlier publication. Before every such push, read the current head-bound independent change/scenario judgment and proof disposition. Check EVERY required registered scenario: actual accepted live proof or an existing explicit approval for its exact missing live claim must be recorded. A successful static check, reviewer saying documentary evidence is sufficient, pending proof or `pass/live:false` without the applicable approval cannot open this gate. Keep successful static results factual without relabeling them live.

If any required disposition is missing, hold the push and record the incomplete story/task and exact criterion/check/evidence dependency. Continue consent-free actual observations and scope-preserving repairs within existing authority, then use the same independent reviewer for affected judgment. Request a precise gap exception only for genuinely unavailable unobserved proof after safe alternatives. An observed ordering failure remains a failure; no exception, subsequent refusal or passing hosted check erases it. After correction, record a distinct subsequent gate observation and independent judgment before publishing again. Hosted checks then verify the published version; merge, activation and deployment remain separately authorized.

### Dependent rollout

After separately authorized integration the first mate replaces the existing project direction in place with the merged method, not a competing rule. Conflicting directions and documents stop affected work until reconciled. A real fresh session reads actual merged method/direction versions and classifies real authorized small/significant cases without unauthorized sample implementation. Record inputs/readings, reasons, actual zero/five phase assignments as they become input-ready, final readiness trilogy-analysis owner, completed results and an actual delivery/proof chain. Missing cases, launches or proof stay explicit first-mate dependencies. Repository alignment is not activation or operating proof; no measured cost/latency saving is claimed.
