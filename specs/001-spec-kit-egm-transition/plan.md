# Implementation plan: Spec Kit and EGM workflow transition

**Specification:** [spec.md](spec.md) (`spec-kit-egm-replacement-v1`)
**Review classification:** Workflow change; all five EGM phases
**Source:** Existing installation with Spec Kit 1.2.5, EGM port 0.9.1 and preset 0.1.1

## Summary

Replace the active custom development manual with a versioned constitution and concise integration guide. Spec Kit feature artifacts own requirements (`spec.md`), the technical approach (`plan.md`) and its derived execution checklist (`tasks.md`); EGM drafting refines the same plan. This is a documentation and agent-instruction transition, not a change to the astrology application. Product rules, historical records, the existing product and technical tracker roles, and host permission boundaries remain. There is one canonical issue per outcome, not a second backlog.

The captain's accepted plan and actual submitted choices are recorded in the host task/card record. The first mate reads that record, then starts or resumes the existing implementation task as the sole owner of the branch and pull request. It passes the exact accepted specification, version and selected review policy into each assignment; each receiving owner reconciles them against the current work before proceeding. This handoff does not infer merge permission. For this transition, the accepted choice is proportionate review and the workflow change requires all five phases.

A Spec Kit preset is a versioned collection of overrides selected by its native resolver. The local preset retains reasoned recommendations, separate review-stage reports and feature/task issue matching, and adds a technical-plan template. It does not introduce another runner. The old manual is deleted, not renamed as another active rulebook. The captain separately decides merge and deployment; this plan does not grant either permission.

## Technical context

Files are project-local. Spec Kit 1.2.5 and the independently maintained EGM port 0.9.1 stay pinned. No new service, global plugin, data model or external interface is needed. The project gate is `npm run check`, then `npm run build && npm test` because tests read the built output.

Before this transition, `.specify/extensions.yml` has an empty `hooks` map but sets `settings.auto_execute_hooks: true`. The transition changes that setting to `false`, retaining `hooks: {}`. The existing `.specify/integration.json` records Codex `events: false`; it is not the same control as hook execution. `.specify/workflows/speckit/` contains a bundled workflow definition, but this transition does not start it or install a second runner. Inspect these configuration values and the workflow registry without executing hooks, events or the workflow; file presence and settings alone do not prove runtime behavior.

## Constitution check

The replacement retains existing product invariants, established tracker roles, host authority and separate permissions. The selected policy is proportionate: this workflow change requires all five EGM phases. Fresh reviewer boundaries, actual inputs, statuses, findings and dispositions must be retained. Missing reviewers and unresolved blocking findings stop completion rather than becoming clean reviews or self-review.

## Project structure

This feature directory contains `spec.md`, `plan.md`, `tasks.md`, `research.md`, `quickstart.md` and `checklists/requirements.md`. The constitution and integration guide point to the existing architecture, invariants, decisions and engineering history. No data model or external contract artifact is needed.

## Detailed Implementation Plan

1. Remove `docs/process/development-process.md`; replace its root pointer in `AGENTS.md` and navigation in `docs/README.md`. Preserve framework, background-server and file-length rules. The standing project direction is reconciled by the first mate only after separately authorized integration, not by changing saved directions during this work.
2. Fill `.specify/memory/constitution.md` at 1.0.0 and update `docs/process/spec-kit-egm.md` for artifact ownership, selected review routing, existing tracker roles and host limits. Add `docs/decisions/0010-spec-kit-egm-workflow.md`, index it and append factual `RECORD.md` history without rewriting earlier entries.
3. Set `.specify/extensions.yml` automatic hook execution false and retain the empty hook map. Leave the Codex event setting false and the bundled workflow dormant. Inspect configuration and registry statically; do not activate any of them to prove they are disabled.
4. Update the versioned source `.specify/local-presets/firstmate-astro-pilot/preset.yml` to 0.2.0. Its `commands/speckit.egm.draft.md` reads the accepted feature specification and refines the existing feature plan; its `templates/plan-template.md` retains summary, technical context, constitution check, project structure and complexity accounting, and adds this `## Detailed Implementation Plan` review boundary. The existing `commands/speckit.egm.review.md` and `commands/speckit.taskstoissues.md` overrides retain stage-specific reports and feature/full-task-ID matching. Do not patch upstream packaged EGM commands or generated skills independently.
5. Run `specify preset update firstmate-astro-pilot --dev .specify/local-presets/firstmate-astro-pilot`. It installs the three command sources and plan template at matching paths under `.specify/presets/firstmate-astro-pilot/`, updates `.specify/presets/.registry`, and materializes the draft, review and task-to-issues skills under `.agents/skills/`. Of the other six EGM skills, review uses the preset override and the remaining five use extension commands; preset resolution selects the configured override rather than the packaged command. Inspect all generated changes, including the existing review and task-to-issues skills; their behavior must retain the earlier fixes. Run the update a second time and compare SHA-256 values of the draft, review and task-to-issues skills and installed plan template before and after: identical content is the reproducibility signal.
6. Run `specify preset resolve` for `speckit.egm.draft`, `speckit.egm.review`, `speckit.taskstoissues` and `plan-template`. Success means exit zero and the installed preset at 0.2.0 selects, respectively, `commands/speckit.egm.draft.md`, `commands/speckit.egm.review.md`, `commands/speckit.taskstoissues.md` and `templates/plan-template.md` under `.specify/presets/firstmate-astro-pilot/`. Check each selected file exists and matches the corresponding versioned local preset source; the selected path and version alone do not prove the generated skill executes correctly. Also run `.specify/scripts/bash/resolve-template.sh plan-template` and compare its output byte-for-byte with the versioned local plan template. Native template composition needs Python 3 with PyYAML. The supported `SPECKIT_PYTHON_EXECUTABLE` override takes a Python executable path or command; verify a candidate with `<python> -c 'import sys, yaml; print(sys.version_info.major, yaml.__version__)'` and use it only if it exits zero and reports major version 3. If the shell default lacks PyYAML, an available Spec Kit Python environment may satisfy this check. Retain commands, output, exit status, checked commit and before/after hashes. A failed resolver is a failure, not a successful preset demonstration. Inspect the seven installed command definitions against the new authority: `.agents/skills/speckit-egm-brainstorm/SKILL.md`, `.agents/skills/speckit-egm-draft/SKILL.md`, `.agents/skills/speckit-egm-bootstrap/SKILL.md`, `.agents/skills/speckit-egm-drift-report/SKILL.md`, `.agents/skills/speckit-egm-resolve/SKILL.md`, `.agents/skills/speckit-egm-review-loop/SKILL.md` and `.agents/skills/speckit-egm-review/SKILL.md`. Separately inspect their shared `.specify/extensions/egm/resources/execution_instructions.md`; it is common material, not an eighth command. Report unresolved references, personas and delegation as gaps.
7. The first mate coordinates five separately attributed EGM review phases on this technical plan. A fresh reviewer receives a new context without the author's conversation or other reviewers' findings; this is a procedural boundary, not a filesystem sandbox. Give each reviewer its explicit packaged persona file, phase instructions, the plan and exact version/hash. Give the canonical feature specification as declared design context to every phase except standalone comprehension; comprehension receives the plan alone as design input, with no author explanations or specification. Keep mandatory host/project instructions visible.
   - **Initial zoom out:** `agents/zoom_out.md` and `agents/inventive_catalyst.md` examine the whole plan and its declared specification context for scope, unnecessary complexity and false compromises.
   - **Comprehension:** `agents/comprehension.md` independently paraphrases what the plan proposes and how the existing system works from the plan alone; retain its complete paraphrase and findings.
   - **Design critique:** `agents/design_critic.md`, `agents/structural.md` and `agents/style.md` examine the relevant plan against the declared specification for design, structure and clarity.
   - **Intermediate zoom out:** `agents/zoom_out.md` checks the whole revised plan and declared specification after comprehension and critique dispositions, focusing on additions and mitigations.
   - **Implementation readiness:** `agents/implementation_readiness.md`, `agents/codebase_details.md` and `agents/style.md` review the detailed implementation section against the declared specification and applicable readiness standard.

   For each phase, the first mate identifies the committed plan and, where allowed, specification by full commit and SHA-256. The first mate uses its existing `spawn_crewmate` task operation with the project `repo_id` and `branch_from` set to the builder task, supplying the explicit target and persona paths, hashes, phase procedure and procedural allowlist constraints. The spawned reviewer owns its task's host-provided evidence folder; it saves and reopens its attributed report there and returns its full path and hash, actual reads and any gaps. A worker is not expected to possess the first mate's launcher. Supply exact files or immutable retained copies through that handoff and ask the reviewer to verify the received bytes against the declared hashes before assessing them. The assignment names the complete permitted design-input list and explicitly excludes author conversation and other reviewers' findings; comprehension's list contains the plan only. The reviewer records which files were actually read, their hashes or source version, mandatory instructions present, and any material it could not inspect. The coordinator compares that record with the assignment and retains it with the attributed report. These are procedural controls and reported observations: they do not enforce a filesystem sandbox or prove that no undeclared context was technically accessible. If received inputs or the boundary cannot be established, record the review as incomplete rather than inferring isolation.

   The phase coordinator saves and reopens its synthesis in its own task evidence folder. For each requested reviewer, it records the reviewer task ID, persona, target source version/hash, supplied inputs, actual reads, procedural boundary, findings and disposition, and completed or not-run status. A complete handoff has the attributed report path/hash and these records for every requested reviewer, plus the synthesis path/hash; missing records prevent a claim of completion. A reviewer who fails, times out or cannot be launched is not run, not a clean review. Resolve or explicitly disposition findings under host authority; an unresolved Blocker or Major prevents advancing. Preserve loop limits and distinct stage reports. Coordinated host tasks demonstrate those reviews only, not automatic EGM spawning, registration or nesting.
8. Demonstrate the selected review routing using bounded examples, without implementing unrelated product work. A wording-only documentation correction with no behavior, shared contract, saved-data or security impact routes to comprehension; an already understood repair without those impacts routes to implementation readiness. A repair is already understood when its defect, affected scope and expected correction are established by the assigned evidence and no consequential design decision remains; otherwise use all five phases. A workflow change such as this transition, new behavior, a shared contract, or a saved-data/security boundary requires all five phases. The first mate records the classification and reason; ambiguity uses all five. Record each example, classification, reason and observed result, not only a checklist assertion.
9. Exercise adverse handoffs without changing product behavior. If a handoff names a superseded specification, stop and reconcile its version against the accepted scope before proceeding. If a required reviewer is unavailable, record that reviewer as not run and stop the affected review; never label the absence zero findings, substitute the author, or claim automatic delegation. Retain the input, observed response and whether reconciliation or a missing capability remains.
10. At the new committed version, the first mate starts the journey task with `spawn_crewmate`, supplying the project `repo_id`, `branch_from` set to the builder task, the exact commit and the explicit target, skill and source-boundary instructions. The spawned task receives its own host-provided task evidence folder and owns the report and source packet there; the builder does not need a first-mate launcher. Give its assistant this request: use the installed `speckit-egm-drift-report` skill to compare `README.md` and `docs/README.md`, verify claims against relevant committed project sources, and save a differences-only report in that task's evidence folder. The host supplies the project skills list; the assistant selects the named skill, opens `.agents/skills/speckit-egm-drift-report/SKILL.md`, and performs its instructions with its ordinary read and write tools. This skill is an instruction file, not a separate executable. Record whether it was supplied before opening it, the actual request, and the source commit; merely reading these instructions is not a successful journey.

   The assistant reads the two explicit target paths in order and identifies the project files and symbols needed to check their claims. Record each target and supporting path and reason in an explicit allowlist; do not expand it by following links without recording the addition. Capture each allowed file's exact bytes from the assigned commit, for example with `git show <commit>:<path>`, under the task evidence folder's `sources/` directory, preserving project-relative paths. Record its commit, Git blob, SHA-256 and byte count in a manifest and verify snapshot hashes; record missing or unreadable sources as gaps. Save the actual differences-only output as `<task evidence folder>/<date>_DRIFT_REPORT.md`. These snapshots are a bounded evidence packet, not another project copy or backlog. The author uses the checked project files to perform the skill; the packet preserves those exact bytes for the subsequent reviewer.

   Keep the skill input, target version, exact allowlist/manifest, hashes and omitted checks beside that report. The journey task saves and reopens the report and returns its full evidence path/hash, source manifest and actual reads to the first mate. The first mate starts a distinct reviewer through `spawn_crewmate` or directs an existing assigned reviewer through `steer_crewmate`, supplying those paths, hashes, boundary instructions and explicit `sources/` snapshot paths; use `files_from` when the supported handoff must transfer retained files. Do not supply the author's conversation or other reviewers' findings. The reviewer opens those supplied paths with ordinary read tools, rather than invoking an EGM executable or reading an unspecified working copy. The reviewer verifies the report and manifest hashes, records which snapshot contents were actually opened and which were only integrity-checked, and retains attributed findings and any omissions. Do not infer content review from a matching hash. The boundary is procedural; host instructions remain present and no filesystem sandbox is claimed.

   The reviewer saves and reopens its report in its own task evidence folder and returns the full path/hash and actual reads. The coordinator saves and reopens a synthesis in its own task evidence folder, recording the journey and reviewer task IDs, persona, source version/hash, supplied and read inputs, procedural boundary, findings, dispositions and missing status. The handoff is complete only when both attributed reports and the synthesis have retained paths/hashes and these records; a missing reviewer or blocking finding remains a gap, not a pass. This does not prove runtime behavior, deployment, exhaustive source coverage or automatic EGM delegation.
11. Run the complete project gate and retain actual output and version. Obtain the applicable independent change review separately from the five design phases, and current hosted checks for the existing pull request. Earlier-version passes are historical. The first mate verifies the revised standing direction and actual reads of new project artifacts in a fresh session only after separately authorized integration.

## Complexity tracking

The local preset remains because removing it would restore known report-overwrite and cross-feature task-identity defects and the upstream no-recommendation rule. Native preset resolution is the existing mechanism; no new scheduler, workflow engine or model-delegation subsystem is introduced.
