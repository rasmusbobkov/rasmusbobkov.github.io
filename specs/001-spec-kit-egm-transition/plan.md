# Implementation plan: Spec Kit and EGM workflow transition

**Specification:** [spec.md](spec.md) (`spec-kit-egm-replacement-v1`)
**Review classification:** Workflow change; all five EGM phases
**Source:** Existing installation with Spec Kit 1.2.5, EGM port 0.9.1 and preset 0.1.1

## Summary

Replace the active custom development manual with a versioned constitution and concise integration guide. Spec Kit feature artifacts own requirements (`spec.md`), the technical approach (`plan.md`) and its derived execution checklist (`tasks.md`); EGM drafting refines the same plan. This is a documentation and agent-instruction transition, not a change to the astrology application. Product rules, historical records, the existing product and technical tracker roles, and host permission boundaries remain. There is one canonical issue per outcome, not a second backlog.

The first mate reads the latest actual submitted decision and values from the resolved host task/card record; they supersede earlier report defaults and unresolved proposals. It starts or resumes the existing implementation task as sole branch and pull-request owner, after verifying its current owner, branch, version and scope. If those differ from the accepted specification, reconcile the mismatch before work; ask only genuinely new scope decisions that belong to the captain. Pass the exact accepted specification, version and selected review policy into each assignment; each receiving owner reconciles them against current work. This handoff never infers merge permission. For this transition, the accepted choice is proportionate review and the workflow change requires all five phases.

A Spec Kit preset is a versioned collection of overrides selected by its native resolver. The local preset retains reasoned recommendations, separate review-stage reports and feature/task issue matching, and adds a technical-plan template. It does not introduce another runner. The old manual is deleted, not renamed as another active rulebook. The captain separately decides merge and deployment; this plan does not grant either permission.

## Technical context

Files are project-local. Spec Kit 1.2.5 and the independently maintained EGM port 0.9.1 stay pinned. No new service, global plugin, data model or external interface is needed. The project gate is `npm run check`, then `npm run build && npm test` because tests read the built output.

Before this transition, `.specify/extensions.yml` has an empty `hooks` map but sets `settings.auto_execute_hooks: true`. The transition changes that setting to `false`, retaining `hooks: {}`. The existing `.specify/integration.json` records Codex `events: false`; it is not the same control as hook execution. `.specify/workflows/speckit/` contains a bundled workflow definition, but this transition does not start it or install a second runner. Inspect these configuration values and the workflow registry without executing hooks, events or the workflow; file presence and settings alone do not prove runtime behavior.

## Constitution check

The replacement retains existing product invariants, established tracker roles, host authority and separate permissions. The selected policy is proportionate: this workflow change requires all five EGM phases. Fresh reviewer boundaries, actual inputs, statuses, findings and dispositions must be retained. Missing reviewers and unresolved blocking findings stop completion rather than becoming clean reviews or self-review.

## Project structure

This feature directory contains `spec.md`, `plan.md`, `tasks.md`, `research.md`, `quickstart.md` and `checklists/requirements.md`. The constitution and integration guide point to the existing architecture, invariants, decisions and engineering history. No data model or external contract artifact is needed.
